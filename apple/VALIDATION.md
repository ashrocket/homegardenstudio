# Native verification

The standard native profile keeps the plan canvas primary, with a collapsible library and inspector. Model changes go through the Rust bridge. Direct manipulation previews an engine transform and commits once; native UndoManager actions use engine history. Pinch zoom cancels a pending drag, and the inspector provides non-drag alternatives and an explicit Done control. Calibration offers point selection and pixel-coordinate fields without claiming measured positions.

On 2026-11-01, the selected Xcode 26.6 toolchain built the universal macOS, iOS device and arm64 iOS Simulator Rust XCFramework. The final phase-B macOS application, asset catalog and test bundle compile, and all 96 tests pass. Current evidence is `apple/build/logs/promotion-macos.log`. The final arm64 iOS Simulator build also passes, including accessibility identifiers and the inspector dismissal control; current evidence is `apple/build/logs/promotion-ios-simulator.log`.

The 96 tests include 25 account/gateway tests, 11 purchase tests, 20 render recovery tests, 18 native engine/document tests, five local assistant tests, two external-drop tests, three render-attachment/sponsorship tests, four quote-precision/account-presentation tests and eight promotion tests. They cover strict FFI input, original-byte preservation, combined attachment limits and atomic import failure, stable project identity, PNG provenance/corruption, free-plan retained access, explicit account recovery, origin pinning, durable render retry/acknowledgement and deletion fencing. The drop fixture checks both accepted PNG/PDF bytes and rejected unsupported input. The presentation regressions cover micro-USD amounts, exact account/origin filtering, and suspended image completions after account switching or recovery deletion. Promotion tests cover the exact 90-day boundary, missing terms, approved StoreKit price metadata, fresh eligibility before checkout, expiry during metadata refresh, and late accepted/unfinished/restored transactions without another local credit grant. Mocked services do not establish real synchronized Keychain, verified AppTransaction, Apple purchases, cloud provider execution or on-device model availability.

The final SwiftUI static audit reports no high-risk findings across 35 scanned files. Twelve medium observations cover canvas/width GeometryReaders, the library's bounded wide-window width, bounded image-preview heights, and index identities in stateless issue rows and the two fixed calibration-point slots. The additional motion observation comes from a nonanimated TimelineView that reevaluates offer eligibility once per second; it performs no network polling or visual animation. Three low observations require runtime gesture verification. Geometry readers are intentional drawing/adaptation boundaries; the library appears beside the canvas only with at least 850 points of available width and otherwise uses a sheet.

Original app artwork is generated by `apple/Design/generate_app_icon.py`. All eleven icon slots resolve to correctly sized opaque RGB PNGs; the original garden-plan design uses no private or stock images. The asset catalog compiles for Mac and iOS Simulator. Both built apps also contain `PrivacyInfo.xcprivacy` with declarations matching the audited source; the resource receipt is `apple/build/logs/p2-privacy-resources.json`. Distribution validation remains separate.

Provisional Apple Fidelity review remains 76/100 (platform 12/15, layout 11/15, native semantics 13/15, interaction 15/20, motion/material 11/15, accessibility 6/10, implementation/performance 8/10). This code/build assessment does not establish the skill's runtime hard gates or its 90-point target.

Still required: native interaction and screenshots on Mac, iPhone and iPad; actual document save/reopen and external/library drag/drop; rapid/cancelled gestures; narrow layouts and large type; VoiceOver and keyboard-only use; appearance/contrast and reduced effects; performance sampling for large plans. An isolated iOS UIQA scheme and stable accessibility identifiers support the next bounded interaction tests. Unit-test host launch does not establish these user flows. No distribution signing, TestFlight upload, processing, tester availability or App Store acceptance is established here.
